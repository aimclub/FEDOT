# Контракт подготовки данных

## Назначение

Этот контракт усиливает существующие `create_data` и `TensorData` перед интеграцией
Industrial с актуальным FEDOT. Второй контейнер данных не создаётся.

Основа изменений: ветка `refactor/fedot_1.0.0`, коммит
`5a55f7e13a4a0f325953632ca9a87116ddecd3ec`.

Код Industrial остаётся в `industrial_release_1.0`. Реализация контракта
подготавливается отдельно в FEDOT: изменения контракта алгоритмического ядра
должны предшествовать переключению Industrial на этот контракт.

## Границы изменений

Проверяются следующие свойства:

- Оси признаков и число объектов согласованы с целевыми значениями и индексами.
- Индексы объектов не подменяются индексами столбцов после подготовки.
- Пропуски и удаление строк сохраняют связь с исходными объектами.
- При предсказании используется состояние подготовки тренировочных данных;
  повторное обучение преобразований на проверочных данных не допускается.
- Создание новых данных не меняет переданные массивы, настройки и тренировочный
  контейнер скрытым образом.
- Устройство тензоров определяется явно; временное переключение backend
  не должно оставлять глобальную настройку изменённой после завершения вызова.
- Прямое и обратное преобразования на границе с `InputData` проверяются
  только для поддерживаемых представлений. Неподдерживаемые случаи не должны
  маскироваться потерей метаданных.

Публичные точки входа сохраняются. Не входят в этот этап: перепроектирование
расширений, оценщика и эволюционной оптимизации, перенос моделей Industrial
в FEDOT, переключение зависимости Industrial на новую ветку FEDOT.

## Подход к проверке

1. Выполнить существующие тесты на исходном коммите в изолированном окружении.
2. Добавить адресные тесты для каждого исправленного нарушения контракта.
3. Независимо проверить свойства через публичные точки входа, включая переход
   от обучения к предсказанию и отсутствие изменения входных данных.
4. Повторить исходные тесты после изменений и отделить новые регрессии
   от исходных сбоев и ограничений окружения.
5. Проверить синтаксис, форматирование и отсутствие лишних изменений.

CUDA, MPS и распределённое обучение не считаются проверенными по результатам
CPU-тестов. Пропущенные проверки должны быть перечислены в итоговом отчёте.

## Размещение кода

Публичная функция находится в `fedot/api/create_data.py`. Контейнер,
спецификация и правила подготовки находятся в
`fedot/core/data/tensor_data/`. Преобразования совместимости находятся
в `fedot/core/data/bridges/`.

Новые правила проверки и планирования располагаются рядом с реализацией,
которая ими пользуется. Чтение данных, обучение преобразований и перемещение
тензоров остаются действиями исполнителя, а не частью чистого планирования.

## Статус

Исходная проверка на Python 3.10.0: 221 тест прошёл, три упали,
два модуля проверки GPU пропущены, 27 тестов вне выбранной группы.
Время выполнения: 43,48 с. Команда:

```powershell
python -m pytest tests/api/test_create_data.py tests/core/data tests/core/backend tests/preprocessing tests/core/operations/test_operation_tensordata_contract.py -m unit -q
```

Исходный импорт на Python 3.11.5 блокируется общим изменяемым значением
`DataSpec.task`: этот Python требует `default_factory` для такого поля.
Это исходный дефект, а не регрессия контракта подготовки данных.

При установке по `pyproject.toml` также обнаружены недостающие обязательные
зависимости `pymonad` и `python-dotenv`. Первая уже указана в
`requirements.txt`; обе нужны для импорта публичного API.
Метаданные дополнены, окружения проверки подготовлены отдельно.

Три исходных падения относятся к устаревшим тестам: ожидание преобразования
`cuda` в `gpu`, старый тип ошибки неизвестного backend и обращение к
удалённому `Operation._wrap_tensor_operation_result`. Последняя проверка
заменена проверкой публичного `Operation.predict`: он должен возвращать
подготовленный стратегией `TensorData` без повторной упаковки и без изменения
входного контейнера. Поведение backend и операций ради старых тестов не меняется.

Итоговая адресная проверка в Windows: по 491 тесту прошли на Python 3.10.0
и Python 3.11.5, по пять проверок пропущены с явными причинами,
одна сетевая проверка исключена. Время: 56,91 с и 57,90 с соответственно.
В набор входят настоящее обучение `torch_linear` через `Fedot.fit`,
повторные `Fedot.predict` и запрет чтения состояния подготовки из файлов
при предсказании числовых и строковых меток классов.

## Реализованный контракт

| Область | Правило |
|---|---|
| `idx` | Одна метка на объект по оси 0; повторяющиеся и строковые метки сохраняются. |
| `idx_mapping` | Отображение подготовленного столбца в исходный столбец, а не отображение строк. |
| Целевые значения | При FIT строка удаляется, если пропущен хотя бы один её целевой компонент. Та же маска применяется к признакам и `idx`. |
| Предсказание | Пропуски в переданных целевых значениях не должны удалять объекты. |
| Признаки | Табличный вектор становится `(samples, 1)`; временной ряд становится `(1, time)`; трёхмерные ряды сохраняют `(samples, channels, time)`. |
| Горизонт | Выделяется по последней временной оси только при FIT, если целевые значения не переданы явно. |
| Состояние подготовки | `PreparationState` хранит схему и отдельные снимки уже обученных преобразований, без исходных массивов. |
| `from_data` | Проверяет схему и повторно применяет обученные преобразования на частных копиях; не обучает их и не загружает трассировку. |
| Имена столбцов | `features_names` соответствует подготовленному порядку. Исходные имена остаются в схеме подготовки. |
| Выбор признаков | Исходное имя или позиция выбирает все полученные из него столбцы; сгенерированное имя выбирает один подготовленный столбец. |
| Устройство | `TensorData.device` определяется фактическим хранилищем; тензорные признаки, цель, предсказания и `idx` должны находиться на одном устройстве. |
| Перемещение | `.to()` явно меняет контейнер на месте, но заменяет поля только после успешного перемещения всех тензоров. |
| Проверка | `.validate()` проверяет форму и устройства без копирования тензорного хранилища. |
| Совместимость | Поддерживаемое преобразование через `InputData` копирует массивы и изменяемые метаданные, включая `Task`. |

Чистые правила проверки, схемы и выбор столбцов отделены от чтения, обучения
обработчиков, кэширования и перемещения тензоров. Исполнитель остаётся
`TensorDataCreator`; второй контейнер или второй алгоритм подготовки не создан.

## Воспроизведение проверки

Из корня отдельной рабочей копии FEDOT выполните в окружении с PyTorch CPU:

```powershell
python -m pytest tests/api/test_create_data.py tests/api/test_create_data_contract.py tests/api/test_create_data_invariants.py tests/api/test_tensor_model_smoke.py tests/core/data tests/core/backend tests/preprocessing tests/core/caching tests/core/operations/test_operation_tensordata_contract.py tests/core/pipelines/test_pipeline.py tests/core/pipelines/test_pipeline_rules.py --deselect=tests/core/data/test_tensor_data_cpu.py::test_loader -q -rs
```

Проверенные версии: PyTorch `2.5.1+cpu`, NumPy `1.26.4`, pandas `2.2.3`,
scikit-learn `1.3.2`, Dask/distributed `2024.4.2`, dask-ml `2024.4.4`.
`cloudpickle>=3,<4` объявлен обязательной зависимостью для снимков состояния.
Проверка установленных зависимостей и компиляция 29 изменённых Python-файлов
прошли в обоих окружениях. Повторное форматирование не даёт различий;
`git diff --check` не обнаруживает ошибок.

## Ограничения и совместимость

- Это адресная проверка контракта подготовки данных, не полный набор тестов FEDOT или Industrial.
- PyTorch CPU установлен явно. Базовая установка FEDOT без PyTorch
  не считается проверенной; политика необязательных зависимостей не менялась.
- CUDA, MPS, Linux и Python 3.12–3.14 в этой проверке не исследованы.
  Два GPU-модуля и одна CUDA-проверка сохранения пропущены без GPU-зависимостей.
- Две проверки transformer-признаков явно пропущены при отсутствии
  `sentence-transformers`; модели и данные не подменяются заглушками.
- Сетевой тест `test_loader` не входит в итоговый набор. В расширенном прогоне
  он прошёл на Python 3.10, но на Python 3.11 столкнулся с общей временной
  папкой двух процессов. Тест теперь направляет загрузку в собственный
  `tmp_path`; повторная сетевая проверка этой изоляции пока не выполнена.
- `use_cache=False` не означает полного отсутствия записи на диск:
  существующий слой трассировки сохраняет план и модели подготовки для
  старого пути по `trace_uuid`. Новый путь `from_data` не читает эти файлы
  при подготовке и восстановлении меток предсказаний.
- Старый одномерный временной ряд с индексом каждого момента времени нельзя
  автоматически считать набором объектов. Преобразование такого `InputData`
  явно отклоняется с `temporal_index_bridge`, а не теряет временные индексы.
- Старые трассировки без сохранённой схемы не позволяют проверить исторический
  порядок столбцов. Для нового кода следует передавать `from_data=train`.
- `TensorData.validate()` проверяет согласованное внутреннее представление
  объектов. Старый завершающий режим прогнозирования может разворачивать
  прогноз в плоский вектор горизонта; его выходной контракт остаётся отдельной
  задачей и не считается доказанным этой проверкой.
- Прямой конструктор `TensorData` заимствует хранилище признаков и цели.
  Изменяемые метаданные копируются; полное владение массивами гарантирует
  `create_data`. Отложенный вызов заимствует источник до первого `get()`.
- Снимки обработчиков используют `cloudpickle` и предназначены только для
  доверенного состояния обучения. Нельзя загружать чужие снимки как безопасный
  формат данных или считать их переносимыми между произвольными версиями.

Новые модели, преобразования расширений, оценщик, параллельное исполнение
и переключение зависимости Industrial остаются задачами следующих PR.
