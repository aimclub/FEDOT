# CPU/GPU: чек-лист объединения операций

7 ноября 2026. Договорённости и вопросы для реализации; порядок пунктов не задаёт порядок работ.
Цель — общий каталог с выбором реализации и устройства для TensorData. Модели и data operations
остаются в отдельных каталогах. Ниже — направления изменений, а не уже реализованный контракт.

## Первая рабочая версия: договорённости 11 ноября 2026

Исходный план ниже сохраняется. Для первой версии пользователь упростил политику:

- cuML допускается только в Linux-окружении с CUDA и установленными зависимостями.
  Windows→WSL исполнение и установщик сейчас не реализуем; существующий отдельный запрет WSL
  не снимать в рамках объединения каталогов без самостоятельной проверки.
- Устройство выбирать по фактическому `TensorData.device` на входе узла. Backend участвует
  в подготовке данных, но изменение глобального Backend не должно переопределять готовые тензоры.
- Выбранные реализация и устройство фиксируются при fit и используются при predict.
  Перенос обученного состояния между устройствами и динамические предпочтения пока не делаем.
- CUDA-вход: доступный CUDA-вариант; иначе CPU-вариант, если он есть. CPU-вход: CPU-вариант.
  Это необходимо для CPU-only моделей в смешанных пайплайнах. Ошибки обучения не маскировать fallback.
- Один ID на логическую модель, один model repository, без пресета `gpu` и отдельных `_gpu` ID.
  Обычные пресеты и отдельный каталог data operations сохраняются.
- Унифицировать применение выбранного исполнения через контракт стратегии: нативным Torch-операциям
  дополнительная настройка не нужна; параметрические модели переводят устройство в параметры библиотеки;
  для sklearn/cuML общий selector выбирает разные стратегии. Не вводить отдельную иерархию адаптеров
  выбора реализации поверх уже существующих стратегий. Подробнее — раздел 1.1 handoff.

Порядок отдельных заданий:

- [x] Контракт метаданных вариантов и детерминированный выбор на примере `rf/rfr` — 11 ноября 2026.
  Ленивые ссылки на стратегии; CPU/CUDA/MPS, ограничения платформ/зависимостей, сохранение `cuda:N`.
  Выбор получает снимок окружения извне, не импортирует стратегии и не обнаруживает оборудование сам.
  Проверено 45 тестов новых контрактов и существующих repository/query/extensions путей.
- [x] Подключить выбор к fit/predict для `rf/rfr`, закреплению и восстановлению обученного состояния.
  Выбор и подготовленные параметры сохраняются в estimator; predict не выбирает исполнение заново.
  Добавлены общий контракт настройки стратегии, проверка совместимости кеша и scope кеша предсказаний.
  `devices` теперь явно указан у варианта модели; sklearn multi-output отмечен отдельной capability.
  Проверено: 106 passed / 6 skipped в sandbox и три smoke-проверки на реальной GPU.
- [x] Перенести каталог/параметры и удалить GPU-пресет, отдельный GPU JSON и `_gpu` дубли — 11 ноября.

Минимальный runtime подключён ко всем перенесённым TensorData-моделям. Нативные Torch data operations
продолжают следовать устройству тензоров. Обычные пресеты сохраняют свой состав и дополнительно
исключают недоступные варианты по платформе, зависимостям и multi-output. Backend по умолчанию остаётся CPU.
Полноценные GPU-пространства тюнинга требуют отдельного согласования: общие CPU-параметры
не всегда допустимы в GPU-библиотеках (например, CatBoost colsample_bylevel).
Подробнее — раздел 1.1 handoff; это не завершение полного плана ниже.

## Полный чек-лист

- [x] **Объединить CPU/GPU-каталоги моделей.** Одна логическая операция (`rf`, `tabpfn`),
  внутри — варианты реализации. Убрать дубли вроде `tabpfn_gpu` и глобальную подмену model repository.

- [ ] **Описать возможности вариантов в метаданных.** Например: `devices: [cpu, cuda]`,
  ссылка на стратегию, предпочтительное устройство/вариант. Различать возможности обучения и inference.

- [ ] **Учесть разные способы поддержки GPU.** TabM/FT-Transformer — одна реализация с выбором
  устройства; sklearn/cuML — разные реализации; бустинги — адаптация параметров и ограничений GPU-режима.

- [x] **Сохранить отдельные стратегии там, где они нужны.** Sklearn и cuML не обязаны становиться
  одной стратегией; общий механизм должен выбирать нужную до её создания.

- [ ] **Проверить общий код CPU/GPU-адаптеров.** Если подготовка target, обработка результатов
  или метаданных повторяется — вынести её в общий базовый класс/помощники. Не создавать базу заранее.

- [ ] **Отделить пользовательское управление GPU от пресетов.** Убрать пресет `gpu`; предусмотреть
  автоматический выбор и явный запрет GPU. Разрешение GPU сохраняет CPU-only операции и предпочтения моделей.

- [x] **Сохранить обычные пресеты.** `fast_train` фильтрует по полю `presets`; `best_quality` использует
  широкий допустимый набор; `auto`, `stable`, модификаторы `*tree` и явный `available_operations` сохраняют смысл.
  GPU не должен добавлять в `fast_train` модели, которые этому пресету не принадлежат.

- [ ] **Выбирать реализацию в общем месте перед созданием стратегии.** Вход: варианты из каталога,
  настройки пользователя, параметры, сведения об оборудовании и фактическом входе узла после родителей.
  Результат: выбранные вариант, стратегия, устройство и параметры; без обучения внутри выбора.

- [ ] **Предпочтения обосновать экспериментами.** Сравнить качество, время и память CPU/GPU,
  особенно sklearn/cuML и бустингов. Поддержка GPU сама по себе не означает предпочтение GPU.

- [ ] **Динамические предпочтения пока отложить.** Если измерения подтвердят пользу зависимости
  от данных — необязательная чистая функция политики операции, вызываемая до создания модели; не условия в JSON.

- [ ] **Разделить устройство TensorData и устройство вычислений.** CUDA-вход у CPU-адаптера
  не делает его GPU-моделью. Согласовать переносы, устройство выхода и их стоимость для смешанных пайплайнов.

- [ ] **Согласовать выбор backend при создании данных.** Сейчас `create_data` по умолчанию явно выбирает
  CPU, даже после глобального `Backend().set('gpu')`. Наметили автоматический выбор с явным переопределением;
  доступность Torch CUDA и доступность полного backend с CuPy/cuDF проверять согласно реальным требованиям.

- [ ] **Разрешить и отдельно проверить cuML в WSL2.** RAPIDS официально поддерживает этот сценарий,
  но `_validate_cuml_environment` сейчас явно его запрещает. Рассмотреть постоянный WSL-процесс для cuML,
  управляемый Windows FEDOT; весь FEDOT переносить в WSL пользователь не хочет.
  Автоматизировать установку окружения отдельным установщиком/командой настройки, учесть elevation и reboot.
  Linux-замер с файлами показал выгоду для крупных KNN/RF, но не всех моделей и не всех режимов inference:
  [результаты](cuml_cpu_transfer_benchmark_2026_11_11.md). Проверка на Linux не заменяет реальную WSL2-проверку.

- [x] **Унифицировать смысл `device='auto'` для выбранного исполнения.** Нейросетевые стратегии
  получают конкретное устройство selector; локальный auto не переопределяет выбор по TensorData.
  PCA/SVD продолжают следовать тензорам, конкретный `cuda:N` сохраняется.

- [ ] **Согласовать параметры вариантов.** Общие гиперпараметры не дублировать; различия sklearn/cuML
  и CPU/GPU-режимов адаптировать локально. Проверить значения по умолчанию и пространства настройки.

- [ ] **Разобраться с `max_samples` / `max_features` foundation-моделей.** Сейчас превышение вызывает
  `ValueError` до обучения, без сокращения данных. Направление — убрать дублирующие запреты FEDOT,
  сохранив реальные проверки библиотек; пороги TabICL отдельно обосновать или удалить.

- [ ] **Не смешивать ограничения с сэмплированием.** Лимиты стоимости относятся к политике поиска;
  уменьшение строк/признаков — отдельный явно выбранный механизм. Не обрезать данные скрытно внутри адаптера.

- [x] **Закреплять обученную реализацию.** Все перенесённые модели сохраняют вариант/устройство/параметры;
  predict, сохранение и кеш используют это состояние без повторного selector.

- [ ] **Предусмотреть переключение устройства inference.** Переносить те же обученные веса/состояние,
  только если реализация это поддерживает. Размер обучающей выборки не задаёт оптимальное устройство inference.
  Механизм и пользовательское управление ещё предстоит определить; смена библиотеки не равна переносу устройства.

- [ ] **Учесть требования среды inference заранее.** Если нужен CPU-inference, допускать только
  соответствующие обученные реализации. Для GPU-only inference не обещать автоматическую замену на sklearn.

- [x] **Сохранять результат выбора и учитывать его в кеше.** Вариант реализации и значимые настройки
  исполнения должны восстанавливаться вместе с обученным узлом и различать несовместимые результаты.

- [ ] **Определить поведение при недоступной реализации.** Поиск исключает неподходящие варианты;
  явный невыполнимый запрос даёт понятную ошибку. Не скрывать ошибки обучения повторным запуском другого алгоритма.

- [ ] **Проверить совместимость с Industrial.** Согласовать смысл устройств и возможностей операций
  с repository/extensions и Industrial; не создавать независимый конкурирующий каталог возможностей.

- [ ] **Обновить проверки и пользовательские примеры.** Покрыть пресеты, CPU-only окружение,
  выбор GPU, смешанные пайплайны, восстановление обученной реализации и поддерживаемый перенос inference.

## Отложенная GPU-поддержка при миграции моделей

Пополнять при встрече новых CPU-only моделей. Отсутствие готового GPU-пути не блокирует TensorData-миграцию;
реализации с существенной дополнительной логикой согласовывать отдельно.

| Модель | Что найдено / что отложено | Возможное продолжение |
| --- | --- | --- |
| Ridge | Для sklearn 1.6.1 Array API есть только с solver=svd; по согласованию оставлен единый CPU-путь. | Использовать существующий cuML Ridge при объединении вариантов. |
| LDA | cuML-аналога в установленном 25.8 нет. Sklearn Array API поддерживает только solver=svd, а FEDOT использует и другие solver, включая fallback lsqr. | Пока CPU; отдельно решить, стоит ли вводить ограниченный Array API-путь или другую реализацию с сохранением параметров. |
| QDA | В установленном cuML 25.8 аналога нет; sklearn 1.6.1 Array API не поддерживает. | Пока CPU; полноценный GPU потребует отдельной реализации, например на Torch, и проверки численной эквивалентности. |
| CNN | Текущая Keras/TensorFlow-реализация умеет GPU, но установленный TensorFlow 2.11.1 не видит GPU даже вне sandbox. | Разбирать на этапе image/CNN: окружение TensorFlow и обмен TensorData, без предположения, что GPU отсутствует в системе. |

KNN classification/regression и SVC уже имеют отдельные cuML-стратегии с TensorData.
При объединении вариантов сохранены коррекция k, смысл p через metric=minkowski и OneVsRestClassifier в CPU-SVC;
наличие cuML-аналога само по себе не гарантирует одинаковые параметры и результаты.
Источники: [sklearn 1.6 Array API](https://scikit-learn.org/1.6/modules/array_api.html),
[cuML API](https://docs.nvidia.com/cuml/latest/api/), [TensorFlow GPU](https://www.tensorflow.org/guide/gpu).


Уточнение по TabPFN/TabICL, 10 ноября: оба семейства уже имеют работающие TensorData CPU/GPU-обёртки.
Их обычные API (TabPFN 2.2.1 / TabICL 2.1.1) всё ещё используют host NumPy/sklearn preprocessing и NumPy
outputs; это не отсутствие GPU inference. Не включать TabPFN differentiable_input ради одного формата:
он меняет preprocessing/ensemble behavior. Возможный native Torch public API будущих версий исследовать
отдельно, сохраняя версии весов и постобработку. Текущие CPU/GPU-aliases и max_samples/max_features
удалены при унификации каталогов 11 ноября; device-зависимые caps сохранены; превышение caps по-прежнему вызывает ошибку без сэмплирования.


11 ноября: scaling/normalization/poly_features — native Torch CPU/CUDA; статистики общие с optional handlers.
KernelPCA/FastICA/DaskPCA и topological_features получили TensorData boundaries, но их sklearn/Dask/ripser
алгоритмы остаются CPU. Их native GPU-перенос отложен: отдельно оценить библиотечные альтернативы,
сохранение параметров/численных результатов и необходимость Dask PCA рядом с уже native Torch PCA.
Это не GPU-вычисления лишь от того, что вход/выход TensorData лежит на CUDA; transfer costs учитывать.


11 ноября, RFE: sklearn fit всех четырёх selectors остаётся CPU; выбор/переиндексация колонок — Torch CPU/CUDA,
проверены CPU↔GPU inference и категории. GPU RFE отложен по согласованию: LinearRegression/LogisticRegression
имеют cuML counterparts, но цикл RFE и параметры/важности нужно согласовать отдельно; прямых публичных
cuML RFE/DecisionTreeClassifier/DecisionTreeRegressor не найдено. Не подменять одиночное дерево лесом
незаметно: это изменяет отбор. Сохранить mask/metadata контракт TensorData.subset_features.


11 ноября, фильтры/resample: resample теперь native Torch CPU/CUDA; числовые значения не переходят
в NumPy/CPU, random sampling использует device-local generator. RANSAC и IsolationForest остаются
sklearn CPU fit (у IsolationForest также CPU predict для training mask), вокруг них Torch calculations.
Отложено: GPU RANSAC требует отдельного решения; GPU IsolationForest есть в новом cuML, но отсутствует
в установленном/закреплённом cuml-cu12==25.8.0. Обновление dependency и согласование masks/параметров
сделать отдельно; нельзя молча включать другой forest. Общая стратегия и row-selection уже TensorData.


11 ноября, decompose: regression/multiclass calculations и подготовка parent rows проверены на CUDA
с запретом numerical cpu/numpy/tolist. Вся арифметика — Torch; дополнительных GPU backend/классов нет.
Роли и глубины выводятся из графа, не из device или новых полей TensorData. Fitted class vocabulary
находится у decomposer; общий producer-class / ragged multioutput contract остаётся отдельной задачей.
