# FEDOT: общий каталог CPU/GPU-реализаций и выбор устройства

Дата: 7 ноября 2026. Снимок: ветка `fedot_1.0.0_new`, HEAD `3c1f4f3d` и рабочие изменения.
Документ предназначен для человека или агента, который не читал обсуждение задачи.
Это описание контекста и предполагаемого решения, а не утверждённая спецификация API или порядок работ.

Короткая версия: [чек-лист CPU/GPU](fedot_cpu_gpu_operations_checklist_2026_11_07.md).
Связанные документы: [результат реструктуризации](fedot_operations_restructuring_2026_11_05.md),
[карта форматов операций](fedot_operations_data_formats_2026_10_09.md),

## 1. Зачем нужна задача и что уже согласовано

Глобальная цель ветки — закончить переход FEDOT на TensorData: модели, data operations,
поиск пайплайнов, оценивание и настройка, включая GPU. Реструктуризация пакета operations уже выполнена.
Теперь перед дальнейшей адаптацией моделей нужно устранить жёсткую привязку CPU/GPU к разным каталогам.

Согласованное направление:

- Один каталог логических моделей с вариантами реализации; каталог data operations остаётся отдельным.
- Одна операция может иметь одну переносимую реализацию или несколько реализаций из разных библиотек.
- Обычные пресеты выбирают состав поиска, а использование устройств управляется отдельно.
- От пресета `gpu` следует отказаться; пользователь должен иметь автоматический выбор и явный запрет GPU.
- GPU разрешён — не значит, что каждая операция обязана выполняться на GPU.
- Предпочтения моделей нужно обосновать измерениями качества, времени и памяти.
- Выбор обучающей реализации и устройство inference — разные решения.

Точное имя пользовательской настройки, схема JSON и контракт переноса обученной модели ещё не выбраны.
Динамические предпочтения по размеру данных обсуждались, но их реализацию решили пока отложить.
Не следует воспринимать примеры названий полей ниже как уже согласованный интерфейс.

### 1.1. Первая рабочая версия: договорённости 11 ноября 2026

Этот раздел задаёт текущий объём реализации. Остальные разделы сохраняют исходный полный план;
описанные ниже упрощения не означают отказ от него. Состояние трёх выполненных этапов зафиксировано ниже.

1. **Платформа.** cuML доступен только в Linux-окружении с CUDA и нужными библиотеками.
   На Windows/macOS такие варианты исключаются. Windows→WSL worker/установщик откладываются.
   Текущий специальный запрет WSL не снимать попутно: его разрешение требует отдельной проверки.
2. **Источник устройства.** Фактический `TensorData.device` на входе узла после родителей.
   Backend определяет устройство при подготовке данных; глобальный singleton не является вторым
   голосом при уже созданном TensorData. Сохранять конкретный CUDA ordinal, например `cuda:1`.
3. **Fit/inference.** Выбранные вариант и устройство закрепляются при обучении. На predict их
   не вычислять заново по новым данным/текущему Backend. В первой версии предполагаем прежнее
   устройство исполнения; перенос обученного состояния и смена библиотеки не реализуются.
4. **Каталоги/пресеты.** Общий model repository, один ID на логическую модель, удаление GPU-пресета
   и `_gpu` дублей. Каталог data operations остаётся отдельным. Существующие обычные пресеты
   продолжают фильтровать логические операции по задаче, типу данных, presets/tags.

Упрощённый выбор: для CPU-входа CPU-вариант; для CUDA-входа подходящий доступный CUDA-вариант,
иначе CPU-вариант, если он есть. Это сохраняет CPU-only модели в GPU-пайплайне и даёт CPU-путь
на Windows для sklearn/cuML пар. При отсутствии допустимого варианта операция недоступна:
поиск её исключает, прямой запрос даёт понятную ошибку. Повторять неудачный fit другой библиотекой
нельзя. Существующий MPS не считать CUDA; не ломать поддерживаемые MPS-пути Torch-операций.

#### Минимальные метаданные

Предлагаемая форма (существующие общие поля операции опущены):

```json
{
  "rf": {
    "implementations": {
      "sklearn": {
        "devices": ["cpu"],
        "strategies": ["fedot.core.operations.strategies.models.sklearn", "SklearnClassificationStrategy"]
      },
      "cuml": {
        "devices": ["cuda"],
        "platforms": ["linux"],
        "requires": ["cuml", "cupy"],
        "strategies": ["fedot.core.operations.strategies.models.cuml", "CuMLClassificationStrategy"]
      }
    }
  }
}
```

`implementations` группирует варианты одной модели; ключ — стабильный ID варианта.
`devices` описывает технически поддерживаемые устройства; `platforms` при наличии ограничивает ОС.
`requires` описывает импортируемые зависимости, но не заменяет проверку реальной CUDA-среды.
Отбирать допустимые варианты до импорта их опциональных стратегий: чтение общего каталога
на CPU/Windows не должно требовать установленного cuML или инициализировать CUDA.
`strategies` сохраняет нынешнее представление ссылки/отображения по задачам. Общие declarations
выносить в существующий metadata-блок, чтобы не копировать cuML-ограничения в каждую запись.
Для переносимых моделей один вариант с `devices: ["cpu", "cuda"]`; два класса не обязательны.

В Python нужны типизированное описание варианта и небольшой результат выбора: ID варианта
и конкретное устройство. Стратегия находится через выбранный вариант и задачу. При predict выбор
можно восстановить по этой паре; хранить только `_eval_strategy` недостаточно, она исключена
из сериализации. Пару сохранять/восстанавливать вместе с обученным состоянием, включая кеш.
Не вводить отдельные поля в TensorData, независимый catalogue of capabilities или новый публичный
переключатель устройства: на этом этапе устройство уже задано размещением данных.

Для одного варианта `devices` достаточно: раздельные fit/predict capabilities, предпочтения,
динамические правила по размеру данных и политика переноса inference остаются в полном плане.
Старые модельные `device='auto'`/CPU/CUDA defaults и параметры бустингов нужно согласовать
с выбранным устройством в одном месте; не оставлять скрытого выбора CUDA внутри CPU-решения.
Явные параметры, противоречащие выбранному исполнению, требуют определённого контракта на границе,
а не разных исправляющих ветвей во всех моделях.

#### Единый контракт применения выбранного устройства

Уточнение после обсуждения трёх способов GPU-поддержки. Разделять два действия:
selector выбирает вариант/стратегию и конкретное устройство; выбранная стратегия применяет это решение.
Не считать два этих действия взаимоисключающими типами операций: альтернативная реализация также
может требовать параметров устройства. Не нужен `adapter_type` с разрастающимся switch в Operation.

| Случай | Выбор | Применение устройства |
| --- | --- | --- |
| PCA/scaling и другие нативные Torch-операции | Одна реализация CPU/CUDA | Работают на входных тензорах; пустой дополнительный шаг настройки |
| TabM/FT-Transformer, бустинги | Обычно одна реализация CPU/CUDA | Перевод выбранного устройства в параметры библиотеки/размещение весов |
| sklearn/cuML | Разные варианты/стратегии | Выбор сделан до создания стратегии; её существующий код готовит данные и вызывает estimator |

Предлагаемый внутренний контракт: стратегия получает результат выбора исполнения до создания
внешней модели. Общая точка настройки по умолчанию не меняет параметры; семейства переопределяют
только необходимый перевод устройства. Для бустингов специфичную адаптацию хранить рядом с соответствующей
реализацией, а не помещать знания о XGBoost/CatBoost/LightGBM в общий selector или Operation.
Нейросетям передавать конкретное устройство, чтобы их прежний `auto` не выбирал заново вопреки решению.

Повторяющийся перевод в обычный параметр `device` вынести в маленький общий помощник, когда он нужен
нескольким реализациям. Отдельные классы-адаптеры оправданы только при самостоятельном повторяемом
поведении; новая обязательная оболочка вокруг каждой стратегии не нужна. Имена методов/способ передачи
контекста в конструктор уточнить при подключении runtime; контракт настроить до создания estimator.

Поддержку CUDA в метаданных объявлять только для фактически работающего пути: параметр GPU у библиотеки
не гарантирует GPU-поддержку установленной сборки или всех режимов задачи. Сохранять конкретный ordinal,
например `cuda:1`. Формат массивов адаптируется существующими конвертерами на границе библиотеки;
общая настройка исполнения сама не переводит весь TensorData через NumPy и не перемещает его целиком.
При predict конфигурация уже закреплена вместе с обученной моделью и не выбирается заново.

#### Реализовано на первом этапе, 11 ноября 2026

- `core/repository/operation_implementation.py`: `OperationImplementationInfo`, ленивый
  `StrategyReference`, enum устройств и платформ, загрузка общих metadata-ссылок/локальных переопределений.
  Поддерживаются одна ссылка стратегии и отображение по задачам; некорректные enum проверяются при чтении.
- `OperationMetaInfo.implementations`: неизменяемый tuple описаний вариантов. Старые поля и
  `current_strategy()` сохраняют прежнее поведение. Только `rf/rfr` получили варианты sklearn/cuML
  в основном JSON; общие устройства/платформы/зависимости объявлены в metadata-блоке.
- `core/operations/operation_execution_rules.py`: чистый `resolve_operation_execution`,
  неизменяемые `ExecutionEnvironment` и `OperationExecutionResolution`.
  Результат содержит ID варианта, конкретный `torch.device` и ленивую ссылку стратегии для задачи.
  Предпочитается устройство входа, затем CPU; при равной пригодности — порядок вариантов в JSON.
  Сохраняется существующее правило совместимых задач из `compatible_task_types`.
- Linux в `ExecutionPlatform` означает native Linux; WSL представлен отдельно, поэтому метаданные
  cuML не расширяют текущую платформенную поддержку незаметно. MPS не смешивается с CUDA.
- Зависимости в переданном снимке обозначают доступные модули. Обнаружение реального окружения,
  импорт выбранной стратегии и настройка параметров относятся к следующему этапу.
  Selector не читает Backend singleton, не импортирует библиотеки моделей и не вызывает CUDA discovery.
- Проверки: 45 passed — новые тесты metadata/selector и существующие operation query,
  repository extensions и pipeline operation repository. GPU/обучение для этого шага не требуются.

Не мигрированным операциям не назначаются предполагаемые CPU/GPU-возможности:
их `implementations` пока пустой, и новый selector для них неприменим. На первом этапе runtime использовал
прежнюю стратегию; состояние подключения описано ниже. Старый GPU JSON и GPU-пресет удаляются после полного переноса.
Алгоритмы моделей и форматы TensorData не менялись; преобразований массивов на этом этапе нет.

#### Реализовано на втором этапе, 11 ноября 2026

- `Operation.fit` выбирает исполнение для операций с `implementations` перед созданием стратегии.
  Сейчас это `rf/rfr` основного каталога. `devices` перенесён в записи вариантов конкретных моделей.
- `operation_execution.py` обнаруживает платформу и импортирует зависимости допустимых по платформе
  и устройству хранения вариантов. Отдельного аппаратного auto-выбора нет: TensorData уже владеет
  тензорами на конкретном устройстве. `ImportError` делает вариант недоступным; другие ошибки
  инициализации не маскируются повторным fit другой библиотекой.
- Добавлено `supports_multi_output` у варианта: sklearn-лес поддерживает несколько target,
  текущая cuML-стратегия — нет. Такой CUDA-вход заранее выбирает sklearn, сохраняя старую функциональность.
- В `EvaluationStrategy` есть общий контракт `configure_execution` / `prepare_execution_params`.
  По умолчанию параметры не меняются; CUDA-контекст обеспечивает конкретный GPU. Для бустингов
  и нейросетей применение параметров устройства подключается при их миграции на общий каталог.
- Обученный estimator остаётся самим estimator. Его `_fedot_execution` хранит `FittedOperationExecution`:
  результат выбора и копию подготовленных параметров. Никаких обёрток над моделью и изменений pickle-путей.
  Существующие joblib/pickle для пайплайна и кеша сохраняют эти данные вместе с моделью.
- `predict/predict_for_fit` используют закреплённое исполнение; стратегия восстанавливается при загрузке
  и переиспользуется для того же fitted state. Обнаружение среды, повторный selector и коррекция
  гиперпараметров по размеру inference-выборки здесь не запускаются. Старый estimator без execution state
  для новой схемы требует refit; совместимость исторических обученных пайплайнов не добавлялась.
- `PipelineNode.fit` отклоняет кешированный fit при несовпадении выбора. Для estimator с execution state
  кеш обученных операций заменяет несовместимое предыдущее состояние по тому же ключу, иначе `INSERT OR IGNORE`
  оставлял бы старую модель и каждый раз требовал refit. Для остальных операций режим кеша прежний.
- Кеш предсказаний разделён по реализации, устройству исполнения, ссылке на стратегию и устройству выхода.
  `Operation.fit` передаёт `descriptive_id` в `predict_for_fit`; раньше он терялся на этой границе.
- Размещение входа inference может отличаться от устройства вычисления: например, GPU-модель cuML
  принимает CPU-данные через прежний адаптер и продолжает считать на сохранённой CUDA. Это не перенос
  обученного состояния на CPU; выход, как раньше, возвращается на устройство входного TensorData.
- Проверки: 106 passed / 6 skipped в sandbox; отдельно 3 passed на RTX 4080 SUPER — cuML `rf/rfr`,
  сохранение/загрузка с CPU-входом inference и multi-output CUDA-вход со sklearn fallback.
  Полные AutoML/WSL-сценарии и новые бенчмарки не запускались.

Изменения кеша/сохранённого исполнения пересекаются с ранее отмеченными контрактами Industrial;
уточнение записано в документ синхронизации. Тела обучения sklearn/cuML и конвертации массивов прежние.

#### Реализовано на третьем этапе, 11 ноября 2026

- Один `model_repository.json`: 66 логических моделей, 54 с вариантами исполнения, 38 с CUDA-путём.
  Устройства указаны у вариантов конкретных моделей. Старый GPU JSON, preset='gpu' и foundation `_gpu` ID удалены.
  Сохранены четыре cuML-only ID (`cd`, `elasticnet`, `mbsgdcregr`, `minibatchsgd`); неработающий `sgd` удалён.
  Ленивый loader позволяет читать каталог на CPU/Windows без импорта cuML.
- Presets и ручной available_operations дополнительно фильтруются по устройству данных, платформе,
  доступным модулям и multi-output. При невозможности CUDA используется допустимый CPU-вариант;
  ошибки fit не вызывают скрытого переобучения другой библиотекой.
- Общий hook `prepare_execution_params`: нейросети получают конкретный device; бустинги адаптируют
  device/device_type/task_type рядом с реализациями. Противоречащий устройству явный параметр даёт ошибку.
  Torch data operations продолжают работать на features.device без дополнительной иерархии адаптеров.
- TabPFN/TabICL объединены под обычными ID; max_samples=None разрешается в прежний device-зависимый cap:
  TabPFN CPU/CUDA 1000/10000, TabICL 5000/30000. Числовой override сохраняется, скрытого sampling нет.
  max_features и остальные параметры сохранены. Исправлено исключение device из kwargs TabPFN:
  раньше библиотечный auto мог проигнорировать CPU-настройку FEDOT.
- Сохранена коррекция слишком большого k; PipelineNode получает исправленные параметры из execution state,
  а не ожидает OperationParameters от cuML.get_params(), который возвращает dict.
  У cuML KNN metric=minkowski сохраняет смысл общего параметра p (его default euclidean игнорирует p=1).
- Публичный CUDA create_data исправлен в source_layout/contracts: tensor idx создаётся/копируется сразу
  на backend device до валидации TensorData. Контракт единого устройства не ослаблен.
- Обновлены help, пользовательская GPU-документация и примеры. Конвертации данных моделей остались
  на существующих библиотечных границах; нового Torch→NumPy ради выбора исполнения нет.
- Проверки: семейства параметров и фильтры, восстановление состояния/кеш, семь коротких fit/predict
  на реальной RTX 4080 SUPER (logit/ridge/KNN/XGBoost/LightGBM/CatBoost/Torch Linear), два случая p у KNN,
  два случая CUDA idx; CPU и CUDA predefined RF через публичный Fedot.create_data/fit/predict.
  Foundation device/caps проверены без скачивания весов; фактический Windows/WSL и полный поиск не запускались.
- Отдельный прежний тест `test_api_params_composer_requirements_do_not_receive_cv_folds` ожидает None,
  но HEAD до этих изменений уже передаёт 3. Это воспроизведённое исходное расхождение; CV-логику не меняли.

Границы минимальной версии:
- Общие пространства тюнинга ещё не адаптированы к возможностям реализации. Например, CatBoost GPU
  отклоняет colsample_bylevel/rsm для обычной classification/regression; его GPU border_count также имеет
  более узкий диапазон. Не удалять параметры молча и не выдавать текущий runtime за готовый GPU-тюнинг.
- LightGBM в установленной сборке работает через OpenCL device_type=gpu; device_type=cuda требует другой
  сборки. OpenCL ordinal и CUDA ordinal не гарантированно совпадают при сложном multi-GPU окружении;
  проверена одна GPU. GPU fit не гарантирует GPU predict: библиотеки могут вычислять inference на CPU.
- Автоматический выбор backend, предпочтения по скорости/качеству, перенос trained state, WSL worker
  и legacy TS/image/text/custom/AutoML остаются отдельными задачами исходного плана.

## 2. Термины и существующие объекты

| Понятие | Пример и смысл |
| --- | --- |
| Логическая операция | `rf`, `tabm`, `pca`: то, из чего поиск строит узел |
| Вариант реализации | sklearn Random Forest или cuML Random Forest |
| Стратегия | Адаптер вызовов FEDOT к семейству реализаций; например, `CuMLClassificationStrategy` |
| Обученный объект | Estimator внешней библиотеки либо FEDOT implementation с обученным состоянием |
| Устройство данных | Где фактически лежит `TensorData.features` |
| Устройство вычислений | Где конкретная реализация выполняет обучение или предсказание |

`Model` и `DataOperation` наследуются от `Operation`. Обычно `node.operation` — оболочка вроде `Model('rf')`,
а `node.fitted_operation` — обученный объект. `Operation._eval_strategy` содержит текущую стратегию.
`strategy.fit` возвращает обученный объект; `Operation.fit` возвращает его вместе с выходом узла для обучения.
Для TensorData модели записывают предсказания в `predict`, data operations преобразуют `features`.

Стратегии находятся в `core/operations/strategies/`, реализации — в `core/operations/implementations/`.
Внутри обоих пакетов модели отделены от data operations. Сохраняем название `EvaluationStrategy`
и термин DataOperation. Возвращать старое дерево `evaluation/` или переэкспорты не требуется.

## 3. Как работали каталоги и пресеты до объединения (история)

Текущее состояние после 11 ноября описано в разделе 1.1: GPU JSON и подмены каталога уже удалены.

Основной каталог — `fedot/core/repository/data/model_repository.json`.
Это не строго CPU-каталог: в нём уже есть GPU-способные нейросети.
`gpu_models_repository.json` содержит cuML-модели и GPU-записи TabPFN/TabICL.
`data_operation_repository.json` регистрируется отдельно.

В `OperationsPreset.filter_operations_by_preset` GPU-ветка вызывает:

```python
OperationTypesRepository().assign_repo('model', 'gpu_models_repository.json')
```

Это глобальная замена активного model repository, а не настройка конкретного `Fedot`.
CPU/GPU-варианты `rf`, `logit`, `ridge` и других операций имеют одинаковые ID, но разные стратегии
в разных файлах. Поэтому механически сложить записи каталогов недостаточно: варианты нужно представить явно.
Состояние глобального каталога может влиять на следующие экземпляры FEDOT в том же процессе.

GPU-ветка формирует `available_operations` только из GPU-каталога моделей. Репозиторий data operations
остаётся доступен, но его записи не объединяются с этим списком. Начальный preprocessing может добавляться
другим путём. Это не цельная политика исполнения графа. TabM/FT-Transformer и другие GPU-способные модели
основного каталога тоже не попадают в данный GPU-пул.

Обычные пресеты работают иначе: `get_operations_for_task(..., mode='all')` собирает операции из активных
репозиториев и фильтрует по задаче, типу данных, тегам и полю `presets`.
Принадлежность `fast_train` записана в `presets`, не в `tags`.

| Пресет/настройка | Текущее поведение, которое нужно сохранить по смыслу |
| --- | --- |
| `fast_train` | Записи, содержащие `fast_train` в поле `presets` |
| `best_quality` | Без ограничения по полю `presets`, но с остальными фильтрами |
| `auto` | Широкий начальный набор; далее выбор `best_quality`/`fast_train` по времени начального обучения и бюджету |
| `stable` | Основа `best_quality` с дополнительным списком исключений |
| `best_quality*tree` | Пересечение базового набора с набором, отмеченным `*tree` в `presets` |
| `available_operations` | Явный пользовательский список; пресет его не перезаписывает |

Обычно исключаются теги `non-default`, `expensive`, `deprecated`; `best_quality` не означает буквально все записи.
Обычные пресеты фильтруют и модели, и data operations. Запрет GPU должен дополнительно ограничивать
варианты исполнения, а не заменять состав пресета. Разрешение GPU не добавляет тяжёлую модель в `fast_train`.
При удалении `gpu` нужно обновить соответствующие тесты, примеры и документацию.

## 4. Где сейчас определяется устройство

`TensorData.device` отражает `features.device`; при прямом создании контейнер сохраняет устройство
переданного Torch-тензора. Метод `data.to(device)` переносит тензорные поля вместе и изменяет объект на месте.

Публичный `create_data` по умолчанию получает `backend=Backend.DEFAULT_NAME`, где `DEFAULT_NAME = 'cpu'`.
Создатель временно переключает `Backend` на запрошенный backend, готовит данные, переносит тензоры
и восстанавливает прежнее глобальное состояние. Поэтому:

```python
Backend().set('gpu')
data = create_data(X, target=y)                  # CPU: у аргумента backend собственный default
data = create_data(X, target=y, backend='gpu')   # запрошенный GPU backend
```

Для `Fedot.create_data` настройка по умолчанию берётся из `tensor_data_config['backend_name']`, тоже CPU.
`backend='auto'` сейчас не поддерживается. `gpu` выбирает совместимый GPU backend, но не откатывается
на CPU при его отсутствии. CUDA-backend подготовки данных сейчас требует также CuPy/cuDF,
тогда как Torch-модели могут использовать CUDA без полного этого стека.

Пользователь хочет в будущем автоматический выбор backend с возможностью явного переопределения.
Нужно согласовать его с модельной политикой, не отождествляя хранение всех данных на GPU
с разрешением отдельной модели обучаться на GPU. Сохранить выбор конкретного устройства `cuda:N`;
учесть уже существующий MPS при уточнении публичного контракта backend.

Исторические локальные defaults внутри реализаций (до общего selector; прямой внутренний вызов
может их сохранять). Теперь публичный runtime передаёт конкретное устройство через hook стратегии:

| Семейство | Выбор устройства сейчас |
| --- | --- |
| TabM, RTDL: FT-Transformer и ResNet | `device='auto'`: доступная CUDA, иначе CPU |
| Torch Linear/MLP, RealMLP | `auto` следует устройству входного TensorData |
| PCA, Truncated SVD | Вычисляют на `features.device`; отдельного device/проверки доступной CUDA нет |
| cuML | Требует CUDA; CPU-признаки переносит на GPU, результат возвращает на устройство входного TensorData |

Нейросетевые реализации могут выполнять подготовку через CPU NumPy, а обучение через CUDA.
Название TensorData-native само по себе не гарантирует отсутствие переносов.
У PCA/SVD при transform сохранённые компоненты и среднее приводятся к устройству и dtype новых признаков.

### 4.1. cuML на Windows / WSL2: уточнение 11 ноября 2026

[RAPIDS официально поддерживает Windows через WSL2](https://docs.rapids.ai/install/#windows-wsl2).
Нативная Windows-установка cuML в поддерживаемых вариантах отсутствует. Docker Desktop с CUDA
также [использует WSL2](https://docs.docker.com/desktop/features/gpu/).
Наш стек пока закреплён на cuML 25.8 / CUDA 12; проверять нужно именно совместимое окружение.

Пользователь предпочитает сохранить FEDOT в Windows и вызывать cuML через постоянный процесс в WSL2.
Это реализуемо: автоматически запускать процесс через `wsl.exe`, передавать запросы и массивы,
оставлять обученные модели в процессе между fit/predict. Существующий DLPack-конвертер сам по себе
межпроцессный обмен не решает. Файлы подходят для прототипа; не запускать Python заново на каждый predict.
На стороне Windows нужен объект обученной операции, обращающийся к WSL-модели; при сохранении пайплайна
сохранять состояние модели, а не только идентификатор живого процесса. Вариант со всем FEDOT внутри WSL
технически проще и избегает межпроцессных передач, но не является предпочтением пользователя.

Установку WSL/окружения можно автоматизировать отдельным установщиком или командой настройки FEDOT.
Обычный wheel/pip не предоставляет стандартного post-install hook для такой системной установки.
Первичное включение WSL может требовать прав администратора и перезагрузки; продолжение настройки
нужно уметь выполнять после неё. Установленные в Windows Python зависимости не устанавливаются в WSL:
cuML и его CUDA-зависимости должны попадать в отдельное Linux-окружение.

`ModelEnginePlan` уже удалён при реструктуризации; исторические документы могут ссылаться на него.
Но `strategies/models/cuml.py::_validate_cuml_environment` всё ещё явно отклоняет WSL по версии ядра,
а `tests/core/operations/test_cuml_strategy.py` закрепляет этот запрет. Для поддержки WSL2 их нужно изменить.
Общий выбор реализации по зависимостям и устройствам всё равно нужен независимо от поддержки Windows.

Полноценную проверку проводить на Windows + WSL2 + NVIDIA GPU. Linux/Docker позволяет проверить
библиотеки, но не Windows-драйвер и WSL GPU-путь. Windows VM с вложенным WSL требует отдельной
проверки виртуализации и доступа к GPU; считать её простым эквивалентом WSL на Windows нельзя.

Не обещать фиксированный процент потерь: [NVIDIA описывает накладные расходы запусков CUDA-ядер
и зависимость от нагрузки](https://developer.nvidia.com/blog/leveling-up-cuda-performance-on-wsl2-with-new-enhancements/).
Есть [ограничения managed/pinned memory](https://docs.nvidia.com/cuda/wsl-user-guide/index.html#known-limitations-for-linux-cuda-applications).
Данные и рабочие файлы лучше держать в [Linux-файловой системе WSL](https://learn.microsoft.com/en-us/windows/wsl/filesystems).
Минимальная будущая проверка: fit/predict cuML, Torch↔CuPy на CUDA и время всего прохода с переносами;
замеры WSL пока не проводились. [Предварительный Linux-бенчмарк](cuml_cpu_transfer_benchmark_2026_11_11.md)
измеряет отдельный постоянный процесс, файлы и переносы CPU/GPU, включая отдельный predict.
Он подтверждает возможность выгоды для части моделей, но не учитывает границу Windows/WSL.

## 5. Предлагаемое представление реализаций

В метаданных операции нужны варианты со ссылками на стратегии и возможностями устройств.
Декларативные факты хранятся в каталоге; условия алгоритма остаются в адаптере.
Необязательно дублировать в JSON каждый estimator, если соответствие уже однозначно задаёт стратегия.

Пример формы записи, **не окончательная схема**:

```json
{
  "rf": {
    "presets": ["fast_train", "*tree"],
    "implementations": {
      "sklearn": {
        "strategy": "fedot.core.operations.strategies.models.sklearn.SklearnClassificationStrategy",
        "fit_devices": ["cpu"],
        "predict_devices": ["cpu"]
      },
      "cuml": {
        "strategy": "fedot.core.operations.strategies.models.cuml.CuMLClassificationStrategy",
        "fit_devices": ["cuda"],
        "predict_devices": ["cuda"]
      }
    }
  }
}
```

Для TabM/FT-Transformer достаточно одного варианта с несколькими устройствами.
Для TabPFN/TabICL убрать отдельные GPU-ID и согласовать параметры одного варианта.
Бустинг может иметь одну библиотечную реализацию с адаптацией CPU/GPU-режима; отдельный класс нужен
только при реальном различии кода. Название библиотеки, устройство и вариант реализации — разные признаки.

Предпочтение задаётся отдельно от технической поддержки. Наличие устройства в списке означает возможность,
а не обязанность его использовать. Списки fit/predict-устройств ещё не описывают все допустимые переносы:
необходимо подтвердить, что конкретное обученное состояние действительно можно перенести между ними.

## 6. Общий выбор перед созданием стратегии

Сейчас `Operation._init` выбирает стратегию через `_eval_strategy_for_task` и
`OperationMetaInfo.current_strategy(task)`. Для одной операции после объединения будет несколько вариантов.
Нельзя сначала создать обучающую модель, чтобы спросить у неё, какую реализацию следовало создать.

Предлагаемая общая граница:

```text
операция + варианты из каталога + настройки пользователя
             + сведения об оборудовании и входе узла
                              ↓
                 выбор реализации и устройства
                              ↓
                создание стратегии → fit → обученный узел
```

Общий выбор получает уже собранные сведения об окружении, проверяет допустимость вариантов
и применяет предпочтение. Сам он не обучает модель, не загружает веса и не переносит данные.
Результат удобно выразить неизменяемым объектом с выбранным вариантом, устройством и параметрами.
Отдельный общий модуль рядом с `Operation`, например `execution_rules.py`, здесь оправдан;
не нужно создавать rules/plan для каждой стратегии или каждого простого преобразования параметров.

Если позже понадобятся динамические предпочтения, допустима необязательная чистая функция политики
операции. В метаданных можно указать её ссылку. Она работает без создания обучающей модели;
условия не превращаются в выражения внутри JSON. Пока достаточно статических предпочтений,
подтверждённых экспериментами. Фиксированные пороги числа строк сейчас не утверждены.

Размер и свойства входа проверяются по данным конкретного узла после его родителей:
encoding/PCA/resampling могут изменить ширину или число строк. При формировании поискового пула
не всегда известен окончательный вход; нельзя отсеивать вариант по неверным исходным размерам.
Доступность библиотек/оборудования можно учитывать раньше и согласованно использовать в начальных
предположениях, генерации/мутациях графа и выполнении узла.

Явный невыполнимый запрос должен давать понятную ошибку. При поиске неподходящие варианты исключаются
с объяснимой причиной. Ошибка fit не должна молча переключать алгоритм, например cuML на sklearn.

## 7. Что можно переиспользовать между CPU/GPU-адаптерами

Возможные общие части: соглашения о target и классах, обработка форм предсказаний,
бинарных вероятностей и метаданных TensorData, общий жизненный цикл estimator.
Перед выделением базы нужно сравнить фактический код sklearn/cuML и других семейств.

Различающиеся части остаются локальными: NumPy/CuPy-представление, переносы устройств,
параметры библиотеки, поддержка multioutput, особенности fit/predict.
Не требуется объединять sklearn- и cuML-стратегии целиком или копировать обучающие циклы нейросетей.
При небольшой общей части достаточно помощников вместо новой иерархии классов.

Общие гиперпараметры не дублировать по CPU/GPU-ID. Зависимые от варианта значения по умолчанию
и пространства настройки должны соответствовать выбранной реализации. Уже есть локальный
`adapt_cuml_parameters`; его смысл нужно сохранить, а не переносить всю адаптацию в общий селектор.

## 8. Ограничения TabPFN/TabICL: что происходит и что менять

В `strategies/models/foundation.py` функция `check_data_size` сравнивает размер обучения
с `max_samples`/`max_features` и выбрасывает `ValueError` до создания и обучения реализации.
Строки и признаки не сокращаются. В implementation эти параметры исключены из аргументов библиотеки.

| Запись в текущих defaults | max_samples | max_features |
| --- | --- | --- |
| TabPFN CPU | 1000 | 500 |
| TabPFN GPU | 10000 | 500 |
| TabICL CPU | 5000 | 500 |
| TabICL GPU | 30000 | 500 |

Таким образом, дубли TabPFN отличаются не только device. Эти адаптеры пока используют старый
InputData/OutputData-контракт: каталог сам по себе не сделает их полноценными TensorData-реализациями.

В установленном TabPFN **2.2.1** уже есть собственные проверки: CPU свыше 1000 строк запрещён
по умолчанию из-за времени выполнения; отдельно проверяются 10000 строк/500 признаков.
Есть `ignore_pretraining_limits` и `TABPFN_ALLOW_CPU_LARGE_DATASET` для соответствующих исключений.
Сейчас увеличение допуска внутри TabPFN не отменяет более ранний запрет FEDOT.
В установленном TabICL **2.1.1** соответствующие фиксированные 5000/30000-пороги в inference-коде
не обнаружены; их происхождение не установлено. Версии библиотек и checkpoint могут менять ограничения.

Намеченное решение — удалить дублирующие запреты FEDOT, оставив реальные проверки библиотек.
Пороги TabICL обосновать либо убрать. Это не гарантия приемлемого времени/памяти на любом размере.
Не смешивать три разных решения:

- техническая поддержка входа — контракт адаптера/библиотеки;
- допустимая стоимость кандидата — политика поиска и бюджет;
- уменьшение данных — отдельный явно выбранный sampling/data operation.

Не создавать универсальные max_samples/max_features для всех моделей ради этих двух семейств.
Не отключать автоматически ограничения библиотеки и не обрезать данные скрытно.

## 9. Обученная реализация и inference

После fit необходимо сохранять выбранный вариант и его обученное состояние.
Для не мигрированных на варианты операций `Operation._predict` ещё вызывает `_init`, выбирая и создавая стратегию.
Для всех перенесённых TensorData-моделей этот путь заменён закреплением исполнения, см. раздел 1.1.
С динамическим выбором этот путь опасен: меньшая тестовая выборка не должна внезапно выбирать
sklearn-стратегию для обученного cuML estimator.

Закрепляется **реализация**, а не обязательное пожизненное использование одного устройства.
Для переносимой нейросети разрешён перенос тех же весов CPU ↔ CUDA без переобучения.
Замена библиотеки cuML → sklearn является другой задачей и не допускается без специально
поддерживаемого преобразования обученного состояния.

Потребуется предусмотреть механизм выбора/переноса устройства inference и управление им пользователем.
Точный API и место вызова пока не выбраны. Не обещать автоматическое переключение по размеру каждой порции:
оптимальный режим inference может отличаться от режима обучения, а переносы имеют собственную стоимость.
Если устройство предсказаний известно заранее, например нужен CPU-only deployment, это ограничение
должно учитываться при допуске обучающей реализации. GPU-only inference нельзя скрытно заменить другим estimator.

Нужно согласовать восстановление варианта при save/load и учитывать его в identity кеша.
Не смешивать результаты несовместимых реализаций под одним ключом `rf`.
Повторное создание стратегии для output_mode допустимо лишь при сохранении выбранного варианта.
Поддержку старых pickle-пайплайнов и прежних импортных путей ранее решили не добавлять:
для них используется соответствующая версия FEDOT. Эта задача не повод возвращать совместимые переэкспорты.

## 10. Что выяснили на примере AutoGluon

Проверялся установленный **AutoGluon 1.5.0, TabularPredictor**; это ориентир, не готовая спецификация FEDOT.
Общий `fit(..., num_gpus='auto')` учитывает предпочтения моделей и доступные ресурсы.
У TabM/RealMLP/TabPFN/TabICL обычно предпочитается CUDA, у CatBoost/LightGBM/XGBoost/NN_TORCH — CPU.
Есть общий запрет GPU и переопределения для отдельных моделей через `ag_args_fit`.
Обычный sklearn RF не заменяется на cuML автоматически; отдельные RAPIDS-классы экспериментальные
и не включены в стандартный реестр моделей.

GPU может менять качество/допустимые параметры бустинга. На малых данных накладные расходы
могут перевесить ускорение. CPU-default в проверенном механизме — предпочтение адаптера,
а не динамическое решение по текущей занятости GPU. Скопировать такие defaults без измерений не следует.

В `AbstractTorchModel` есть отдельные `device_train`, `suggest_device_infer`, `set_device`:
при загрузке предпочитается устройство обучения, при его отсутствии — CPU, если перенос поддержан адаптером.
По числу строк новой порции оно не пересчитывается. У старого NN_TORCH похожая собственная логика.
Для экспериментальных RAPIDS-обёрток автоматического преобразования в sklearn не обнаружено.
Универсальная переносимость GPU → CPU не гарантируется; соответствующие ошибки встречались и у AutoGluon.

Источники исследования:

- [AutoGluon 1.5: fit и управление ресурсами](https://auto.gluon.ai/1.5/api/autogluon.tabular.TabularPredictor.fit.html).
- [AutoGluon 1.5: GPU-настройки моделей](https://auto.gluon.ai/1.5/tutorials/tabular/advanced/tabular-gpu.html).
- [Пример ошибки переноса GPU → CPU, AG 1.4](https://github.com/autogluon/autogluon/issues/5291).
- [TabPFN: настройки и ограничения CPU](https://github.com/PriorLabs/TabPFN#readme).

## 11. Industrial и существующие контракты

См. [отдельную записку](fedot_industrial_tensordata_sync_2026_11_05.md): в Industrial уже есть
декларации возможностей операций и проверка графов. В FEDOT есть repository metadata и
`fedot.extensions`, включая `ModelCapabilities`/`TransformCapabilities`.
Их `backend: numpy/torch` описывает формат на границе адаптера, а не устройство вычислений.

Нужно согласовать общий смысл возможностей, а не создать второй независимый каталог для GPU.
FEDOT не должен импортировать Industrial ради выбора встроенной модели.
Перед реализацией capability/device-контракта вернуться к записке и напомнить пользователю о пересечении.
Кеш и identity обученной реализации — ещё одна точка синхронизации.

## 13. Что проверить при реализации

Проверки должны подтверждать поведение, а не просто воспроизводить ветвления селектора:

- На CPU-машине обычные пресеты сохраняют ожидаемый набор доступных CPU-вариантов.
- При доступном GPU CPU-only операции остаются допустимыми, а GPU не расширяет принадлежность пресету.
- Явный список `available_operations`, `stable`, `auto` и пересечения модификаторов не ломаются.
- GPU доступен для Torch, но CuPy/cuDF/cuML отсутствуют: возможности не смешиваются.
- Пользовательский запрет GPU применяется и к модели, у которой локальный default сейчас предпочитает CUDA.
- Два экземпляра FEDOT с разными настройками не подменяют друг другу каталог/выбор реализации.
- Размер входа оценивается после родительских операций; CPU/GPU-адаптеры сохраняют контракт TensorData.
- У fit и predict разные числа строк: обученная реализация остаётся прежней, в том числе после save/load.
- Поддерживаемый перенос обученной модели сохраняет её состояние и ожидаемые предсказания в допустимой точности.
- Неподдерживаемый CPU-inference обнаруживается согласно контракту, без молчаливой подмены алгоритма.
- Кеш различает несовместимые реализации; классификация сохраняет классы и режимы вероятностей.
- Превышение старых foundation-порогов не запускает скрытое сэмплирование.

Полезные существующие тесты: `tests/api/api_utils/test_presets.py`,
`tests/core/repository/test_operation_query.py`,
`tests/core/repository/test_operation_types_repository_extensions.py`,
`tests/core/operations/test_cuml_strategy.py`, `test_cuml_tensordata.py`, `test_torch_model_config.py`.
GPU-результаты подтверждать реальным GPU-прогоном; анализ кода не заменяет такую проверку.

Перед правками перечитать `AGENTS.md` и рабочий diff. В снимке есть незакоммиченные изменения
`transform_for_fit` в общей базе TensorData data operations/проекциях, тест этого контракта и правка
документа структуры. Это предыдущая отдельная задача, не реализация объединения CPU/GPU.
Каталоги benchmark-результатов также не относятся к этой работе. Не коммитить их вместе автоматически.
